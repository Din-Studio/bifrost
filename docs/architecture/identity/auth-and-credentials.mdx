本页固定 Phase 3 实现"谁在发请求、拿到什么 permit、停用后多久失效"时不得再猜的规则。决策记录见 [Overview](/architecture/identity/overview)，验收 ID 见 [Test Plan](/architecture/identity/test-plan)。

## 1. 认证模式表

有效认证模式不是 `auth_config.is_enabled` 一个布尔量，而是 **password 开启 或 SSO 配置成功** 的合成结果。现状是 `transports/bifrost-http/handlers/middlewares.go:1173-1188` 在 `authConfig == nil || !IsEnabled` 时直接把请求标为 `IsLocalAdmin=true` + `AuthBypassed=true`，这条分支早于任何 cookie 校验；只改 cookie 成功后的分支无法覆盖"只配 SSO、不开 password"的部署。

| Password auth | SSO（`scim_config.enabled` 且初始化成功） | 匿名管理请求 | 已认证请求 | AC |
|---|---|---|---|---|
| 关 | 关 | 保留 OSS 无认证模式：`IsLocalAdmin=true`、`AuthBypassed=true`（`middlewares.go:1173-1188` 原语义） | 不适用 | AC-AUTH-1、AC-CFG-1 |
| 开 | 关 | 401（现状） | admin 账密会话 → `IsLocalAdmin=true`（现状） | AC-AUTH-1 |
| 关 | 开 | **401，绝不进入 auth-disabled bypass**；bypass 判定必须读"有效模式" | user 会话 → `IsLocalAdmin=false`，写入用户身份 | AC-AUTH-2 |
| 开 | 开 | 401 | SSO 用户走 user 会话；break-glass admin 走 admin 会话；两者分别认证、互不提升 | AC-AUTH-5 |

补充规则：

- **SSO 初始化失败不降级。** discovery 不可达、JWKS 拉取失败、`scim_config` 损坏时，管理请求一律拒绝，`GET /api/session/is-auth-enabled` 返回错误状态而不是 `none`。启动期由 `lib.loadScimConfig` 拒绝非法配置（`transports/bifrost-http/lib/configidentity.go`），运行期由 SSO 组件的健康状态决定。AC-AUTH-3、AC-CFG-2。
- **四个入口读同一有效模式。** `is-auth-enabled`（`handlers/session.go:43`）、`/auth/type`、登录页（`ui/app/login/layout.tsx:75-83`）、登出都从同一个"有效模式"函数取值，不各自判断。AC-AUTH-4。
- **HTTPS 门槛不可经 `trusted_networks` 豁免。** `issuerUrl` 必须 `https://`，本地开发只能用 `identity_sync.allow_insecure_issuer_for_dev`，并在启动日志留下 warn。AC-CFG-3。
- Phase 3 前配置变更一律 restart-required（`handlers/config.go:1007-1014` 机制）；DB 持久化与向导留 Phase 4。

## 2. 会话模型

### 2.1 两类会话

| Kind | 产生路径 | `IsLocalAdmin` | ctx 身份 | AC |
|---|---|---|---|---|
| `admin` | `POST /api/session/login` 账密（`handlers/session.go:96-170`） | true | 无 `UserID`（保留现状） | AC-AUTH-1 |
| `user` | OIDC Authorization Code + PKCE 回调 | **false** | `BifrostContextKeyUserID` / `UserName` / `UserEmail`（`core/schemas/bifrost.go:376-379`）+ `RoleID` | AC-SESS-1 |

`SessionsTable`（`framework/configstore/tables/sessions.go:12-20`）增加 `Kind`、`UserID`、`RoleID`。`middlewares.go:1252-1258` 现在"cookie 校验通过即 `IsLocalAdmin=true`"必须改为按 `Kind` 分派；`NULL UserID` 不再无条件视为管理员。Viewer 角色的 user 会话调用写接口时由服务端 RBAC 返回 403（AC-SESS-1、AC-RBAC-3）。

### 2.2 身份进入 grant

user 会话校验后，中间件写入 ctx，`transports/bifrost-http/lib/ctx.go:848` 每请求调用 `SettleIdentity`（`lib/grant.go:44-99`）把 `UserRef` 装进 grant，日志归因由 `plugins/logging/main.go:2015` 免费获得（AC-ATTR-1）。**治理不免费**：`plugins/governance/store.go:1264-1282` 只从 VK 解析 permit，`main.go:722-725` 对"有身份无 permit"返回 `access_not_found`，`permits_test.go:1230-1242` 固定了该行为。因此 Phase 3 经 `InitFromStore`（`plugins/governance/main.go:258-273`）注入装饰 `LocalGovernanceStore` 的 store，为 user 会话与 MCP user-mode JWT 返回**最小用户 permit**（无模型限制、无预算、不记账）。AC-AUTH-7、AC-AUTH-10。

### 2.3 `OAuth2IdentityResolver`

接口在 `transports/bifrost-http/handlers/mcpoauth2consent.go:25-45`。MCP 凭据模式以 `UserID` 为最高优先级（`core/schemas/context.go:414-435`），所以错误身份会改变上游 MCP token 选择，实现必须严格。

| 方法 | 读什么 | 返回 | AC |
|---|---|---|---|
| `ResolveUserIdentity` | 当前请求的 user 会话（cookie / ws-ticket） | `UserID`、`UserName`、`UserEmail`；admin 会话或无会话返回空 | AC-AUTH-10 |
| `ResolveVKUserUpgrade` | `x-bf-vk` 对应 VK 的 user 绑定（绑定表 Phase 3 定义） | 绑定用户身份；未绑定返回空，**不**用 `CreatedByUserID` 代替（`tables/virtualkey.go:292` 是创建者） | AC-AUTH-12 |
| `IsUserActive` | `users.active` | 仅回答身份是否存活；**不**回答授权（`handlers/mcpserver.go:674-676` 已把授权交给 governance） | AC-SYNC-6、AC-DEAC-1 |
| `IsUserModeAvailable` | 第 1 节的"有效模式"（`Config.ScimConfig` 已加载且 SSO 初始化成功） | `true` 时 consent 页才提供 user mode；与 `is-auth-enabled` / `/auth/type` 读同一来源 | AC-AUTH-4、AC-AUTH-3 |

### 2.4 Refresh token 与登录事务

- refresh token 服务端保存、加密存储，复用 `framework/configstore/tables/sessions.go:25-39` 与 `tables/mcpoauth2.go:245` 的 `BeforeSave/AfterFind` hook 模式；cookie 只放不透明会话凭据，不放 IdP token。AC-SESS-2。
- 刷新轮换需处理并发刷新、进程重启、旧 token 重放；复用 `framework/oauth2/sync.go:88-103` 的 gate 思路，但 v1 单实例，不承诺跨副本去重（见 Overview 部署范围）。AC-SESS-2。
- 登出使 session 行与 refresh token 同时失效；重放 cookie 得 401。AC-SESS-3。
- 登录事务硬性要求（`coreos/go-oidc` verifier 不校验 nonce，需应用自做）：
  1. `state` 绑定发起浏览器、一次性消费、有过期；原子消费模式参照 `framework/oauth2/main.go:870-900`、`framework/configstore/rdb.go:7794-7828`，但不混用 MCP token 数据模型。
  2. PKCE `S256`（本地 Casdoor discovery 已确认支持）。
  3. 若发送 nonce，回调严格核对。
  4. 校验 `iss`、`aud`、`exp`。
  5. 重复 / 并发 callback 只有一个成功，其余不创建会话、不留部分授权状态。
  6. 登录后跳转目标限制为站内相对路径。

  AC-AUTH-6。

## 3. 请求凭据矩阵

复审 P1 #1 的六行。列出的行为是 Phase 3 的实现契约。

| 请求凭据 | permit 来源 | 日志 `user_id` | MCP 上游凭据 | 备注 | AC |
|---|---|---|---|---|---|
| 浏览器 user 会话，无 VK | 最小用户 permit（注入 store） | 会话用户 | 用户 grant（`context.go:414` UserID 优先） | 不前移则 dashboard playground 对 SSO 用户直接 `access_not_found` | AC-AUTH-7 |
| 仅个人 VK（SDK） | VK permit（现状 `store.go:1264-1282`） | Phase 3 前为空；VK↔user 绑定落地后为绑定用户 | VK 绑定的 MCP 配置 | 绑定表 Phase 3 定义；用户停用 → 绑定 VK 停用 | AC-AUTH-12 |
| MCP user-mode JWT（`mcpoauth2jwt.go:138-143` 写入身份） | 最小用户 permit（同一原语） | JWT 用户 | 用户 grant | `IsUserActive=false` 或角色清空 → 拒绝 | AC-AUTH-10、AC-SYNC-6 |
| cookie user 会话 + `x-bf-vk` | **VK 决定 permit**（与 `lib/grant.go:72-91` 一致） | 会话用户（只做归因） | 以 UserID 优先（`context.go:426-435`） | user 不放大 VK 权限，也不缩小 | AC-AUTH-8 |
| IdP bearer + VK（含 user A 会话 + user B 的 VK） | 按 `dual_credential_conflict_behavior`（`config.schema.json:157-160`：`error` / `prefer_vk` / `prefer_idp`） | 与 permit 来源一致 | 与 permit 来源一致 | 三者必须同源，不能日志记 A、permit 用 B | AC-AUTH-9 |
| 无任何凭据 | `enforce_auth_on_inference` 开 → 401；关 → 现状放行（`middlewares.go:1074-1089` inference middleware 直接放行） | 空 | 无 | 行为与改前逐字节一致 | AC-AUTH-11、AC-CFG-1 |

## 4. VK 可读性规则

现状 `framework/configstore/tables/virtualkey.go:320-331` 的 `MarshalJSON` 输出明文 `value`，`handlers/governance.go:1599-1633`（列表）与 `:1888-1912`（详情）直接返回。若 Viewer / Developer 拥有全局 `VirtualKeys.View`，就能保存他人或共享 VK，离职回收对这些 VK 无效。

| 规则 | AC |
|---|---|
| 非 Admin 的 `VirtualKeys.View` 只返回脱敏 `value`（`SecretVar.Redacted()` 形式：前 4 + 24 星 + 后 4） | AC-AUTH-13 |
| `VirtualKeys.Reveal` v1 仅 Admin；`RbacOperation` 已有 `Reveal` 枚举，不新造 | AC-AUTH-13、AC-RBAC-4 |
| 验收含"停用后先前读取的凭据是否仍可调用"：脱敏值不可调用；共享 VK 明示不在个人回收 SLA 内 | AC-AUTH-13、AC-DEAC-4 |
| Provider key 已有独立脱敏（`handlers/provider_keys.go:64,90`、`lib/config.go:6899`），不在此规则内 | — |

## 5. 停用 SLA 分面表

官方文档在 15 分钟刷新与按需刷新 / 30 分钟 session floor / 24 小时 sweep / 5 分钟权限缓存之间不一致，本项目分面定义并按复审修正。

| 面 | 目标 | 修正与说明 | AC |
|---|---|---|---|
| 已认证停用写入（SCIM / bridge）后的新 HTTP / MCP 请求 | ≤ 权限缓存周期（默认 5 分钟）内拒绝；单实例即时 | MCP 的"最多 5 分钟"与"`IsUserActive` 即时"统一为同一缓存约定 | AC-DEAC-2 |
| webhook 故障，仅靠扫描 | 更新发现 ≤ `scan_interval`（默认 15m）+ 处理时延；删除发现 ≤ `inventory_interval`（默认 24h） | 15 分钟不是删除的 SLA；删除只有完整 inventory 能发现 | AC-BRIDGE-2、AC-DEAC-2 |
| IdP 响应分类（refresh 路径） | timeout / 5xx → 重试，不停用；`invalid_grant` → 会话失效、查 active；明确 inactive → 停用；明确 not-found → 按删除处理 | **SCIM-only 例外**：refresh 失败只失效会话，不得经 OIDC 路径改 SCIM 管理的 active / role / team | AC-DEAC-3、AC-SESS-4 |
| 角色清空但 `active=true` | governance 在 SLA 内拒绝，不能只靠 `IsUserActive` | 旧 MCP JWT 继续请求必须被拒 | AC-SYNC-6 |
| 长连接 | WebSocket 周期重验 ≤ 5 分钟（`handlers/websocket.go:29-40` 在 upgrade 时快照角色，需加重验）或停用广播即断；MCP grant 经 `IsUserActive` 即时 | v1 单实例，广播为本进程内 | AC-DEAC-6、AC-DEAC-1 |
| 用户绑定 VK | 停用时同步停用 | 共享 VK 无法凭空恢复自然人身份，明示排除 | AC-DEAC-4 |
| 重新激活 | 旧 session / refresh / MCP grant / 个人 VK **不自动复活**；需重新登录、重新授权、管理员重新启用 VK | 避免"只检查 active"造成旧凭据意外复活 | AC-DEAC-5 |

## 6. 失效面清单

停用或角色变更必须覆盖以下全部面；缺一项即视为 AC-DEAC-1 失败。

| 失效面 | 位置 | 动作 | AC |
|---|---|---|---|
| session 行 | `SessionsTable`（`tables/sessions.go`） | 删除或标记失效；cookie 重放 401 | AC-DEAC-1、AC-SESS-3 |
| refresh token | 加密列 | 删除；后续刷新 `invalid_grant` | AC-DEAC-1、AC-SESS-2 |
| WebSocket 连接 | `handlers/websocket.go:29-40` 快照 | 周期重验或广播断开 | AC-DEAC-6 |
| MCP grant / user-mode JWT | `handlers/mcpserver.go:678` `IsUserActive` | 请求与刷新时切断 | AC-DEAC-1、AC-AUTH-10 |
| 用户绑定 VK | VK↔user 绑定表（Phase 3） | 同步停用 | AC-DEAC-4 |
| 权限缓存 | RBAC 判定缓存 | ≤ 5 分钟过期或即时失效 | AC-DEAC-2 |

多实例失效传播不在 v1 范围（AC-ATTR-4 标注为不适用），Overview 已声明单实例。
