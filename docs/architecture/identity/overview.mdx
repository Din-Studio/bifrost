## 六层分工

沿用仓库既有的 `framework/oauth2` + `handlers/mcpoauth2*.go` 分层：

| 层 | 职责 | 复用契约 |
|---|---|---|
| Framework storage（`framework/configstore`） | 既有表；本项目只为 configstore 自有表加列（`sessions.kind/user_id/role_id`、VK 的 user 绑定） | `ConfigStore.DB/ScopedDB/RunMigration`，`tables/sessions.go` 与 `tables/mcpoauth2.go` 的 token hooks |
| Framework identity（新包 `framework/identity`） | users / roles / permissions / user_identities / user_teams / scim_* / identity_sync_* 表与迁移；登录身份解析、claim memory、同步模式与来源规则、停用、共享写入服务 | `ConfigStore.RunMigration` / `RunSingleMigration` 在同一 `*gorm.DB` 上建表；对外只暴露自己的窄接口 |
| Casdoor adapter（`framework/identity/casdoor`） | 目录 API、webhook 信号、增量扫描、完整 inventory 对账，输出标准化目录变化 | 调用 identity 写入服务；独立于 generic OIDC RP |
| Transport（`transports/bifrost-http`） | OIDC / SCIM / Users / RBAC 路由族、凭据校验、管理接口授权、身份写入 ctx；`lib.ConfigData` 的 `scim_config` / `identity_sync` 类型化（**Phase 1 已落地**） | `RegisterAPIRoutes`、middleware、`OAuth2IdentityResolver`、`lib/grant.go` 的 `RecordUser` / `SettleIdentity` |
| Governance plugin | 用户 / 团队访问许可、模型权限、预算限流记账 | `InitFromStore` 注入、`ResolvePermits`、`GatherLimits`、`grant` |
| Data access | own / team / all 行级与聚合边界（Phase 5） | `queryscope`、`ConfigStore/LogStore.ScopedDB` |
| UI | SSO login / refresh、真实 `RbacProvider`、Users 页 | 现有 `@enterprise` 接口面、entity selector registry、导航 hooks |

依赖方向是硬约束：**identity → configstore；configstore 永不 import identity；governance 通过注入而非 import 拿到用户 permit。**

## 装配决策记录

### D1 存储装配：组合式 `framework/identity`

| 决策 | 备选 | 证据 |
|---|---|---|
| 新包 `framework/identity` 拥有身份表与迁移，通过 `ConfigStore.RunMigration` + `RunSingleMigration` 在同一 DB 建表，对外暴露窄接口；configstore 自有表需要的新列走 configstore 自己的迁移；governance 在 Phase 3 改用 `InitFromStore` 注入一个装饰 `LocalGovernanceStore` 的 store | 直接扩展 `ConfigStore` 接口：编译成本低（唯一实现是 `RDBConfigStore`），但把 8 张身份表塞进已 339 方法的接口，与 `rdb.go:6173` "owner table out of package" 的既有边界相反，与上游 `dev` 合并冲突面最大 | `framework/configstore/store.go:998-1032`（`DB` / `ScopedDB` / `RunMigration`，注释写明面向 downstream-consumer 迁移）；`migrations.go:156-172`（`RunSingleMigration` 为 "downstream consumers (bifrost-enterprise, plugins)" 而设）；`rdb.go:6172-6183`（user scope 的 owner table "out of package"）；`tables/mcpoauth2.go:395-413`（`OauthUserSummary` 由 enterprise wrapper post-fetch 填充，OSS 留 nil）；`plugins/governance/main.go:258-273`（`InitFromStore`）；`framework/webhooks/dispatcher.go:19-27`（消费方声明窄接口的先例） |

三条规则：

1. 依赖方向 identity → configstore，反向禁止。
2. configstore 自有表的新列（`sessions`、`virtual_keys`）走 configstore 迁移；identity 自有表走 identity 迁移，两者在同一 `*gorm.DB` 上按版本顺序执行。
3. governance 只通过 `InitFromStore` 注入的 store 看到用户 permit；`plugins/governance` 不 import `framework/identity`。

### D4 配置生命周期分期

| 阶段 | 行为 |
|---|---|
| Phase 1（已落地） | 只读 `config.json`；`LoadConfig` 阶段类型化并校验；密钥字段（`clientSecret`、`provisioningToken`、`webhook_secret`）为 `schemas.SecretVar`，支持 `env.` 前缀；不写 DB、不经 `/api/config` 暴露 |

| Phase 4 | DB 持久化、文件与 DB 优先级、向导（Should）、hot reload；API 响应必须显式调用 `SecretVar.Redacted()`——`SecretVar.MarshalJSON`（`core/schemas/secretvar.go:320`）输出明文，**不会**自动脱敏 |

### D5 HTTPS 与本地 Casdoor

正式路径要求 `issuerUrl` 为 `https://`；`scim_config.trusted_networks` 只影响 SSRF 出站白名单，**不豁免** HTTPS。开发环境用 `identity_sync.allow_insecure_issuer_for_dev: true` 显式放行 `http://`，启动时 `logger.Warn` 一次。验收：AC-CFG-3。

### D8 认证总开关、VK 可读性、身份绑定、删除判据

这四项的决策分别落在 [auth-and-credentials](/architecture/identity/auth-and-credentials)（认证模式表、VK 可读性）、[identity-binding-and-sync](/architecture/identity/identity-binding-and-sync)（绑定键、删除判据）。本页只记结论：

- 有效认证模式 = password 开启 **或** SSO 配置成功；SSO 初始化失败不得降级为无认证（AC-AUTH-2、AC-AUTH-3）。
- 非 Admin 的 `VirtualKeys.View` 只返回脱敏值；`Reveal` v1 仅 Admin（AC-AUTH-13、AC-RBAC-4）。
- `sub == Casdoor User.Id`（UUID）是唯一跨系统键；桥接写 `external_id = User.Id`；email / name 永不作合并键（AC-BIND-1、AC-BIND-2）。
- 目录中"不存在"以 `get-user?userId=<uuid>&owner=<org>` 返回 `data: null` 为准（AC-BRIDGE-6）。

## Phase 1 实测修正

Phase 1 在本机 Casdoor v4.1.0（commit `9603cdd`，2026-09-16）抓取样本时发现两处与计划假设不同，已写入 [casdoor-bridge](/architecture/identity/casdoor-bridge)：

1. **webhook 的 `extendedUser`、`Record.user`、`Record.organization` 是操作者，不是受影响用户。** 受影响用户在 `Record.object`（请求体 JSON 字符串）里；`add-user` 的 object 没有 `id`。桥接主体必须从 `Record.object.owner/name` 取并回查，`isUserExtended` 对主体识别没有帮助（AC-BRIDGE-5）。
2. **Casdoor 投递 worker 只在启动时已存在 webhook 才会启动**（`object/webhook_worker.go` `StartWebhookDeliveryWorker` 的 `HasAnyWebhooks` 门）。启动后新建的 webhook 事件永远停在 `Pending`，直到 Casdoor 重启。运维步骤必须是"先建 webhook 再重启 Casdoor"，且扫描 + inventory 路径必须能独立收敛（AC-BRIDGE-10、AC-BRIDGE-3）。
